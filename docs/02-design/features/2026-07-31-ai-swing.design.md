## 1. 목적

### 1-1. 풀려던 문제

사용자가 매일 새벽 텔레그램으로 받는 **"주식단테" 분석이 실제 매매에 한 줄도 반영되지 않았다.**

| 확정 사실 | 근거 |
|---|---|
| 발신원 = `/Users/beye/workspace/ai-trade` (독립 레포) | — |
| 변경 전 예측 결과 `pred_results` 는 로컬 변수 → 텔레그램 발송 후 소멸했음. 현재는 발송 전 당일 파일로 원자 저장한다. | `ai-trade/main.py` 예측 완료 훅 |
| `shared.prediction_scores` 를 읽는 진입 태스크는 `regular_trading_enabled: false` 로 **생성 자체가 안 됨** | `ai-trade/config/settings.yaml` |
| BarroAiTrade 신규 경로는 legacy 파라미터를 참조하지 않음 | 구현 확인 |

### 1-2. 진단 — 문제는 승률이 아니라 손익비다

브로커 실측 (`data/kiwoom_trade_history_1y.db`, mock, 2026-06-05~07-10, n=162):

| 지표 | 값 |
|---|---|
| 승률 | 29.0% |
| 평균익 / 평균손 | +3.735% / -3.816% |
| **손익비** | **0.98** |
| 자본가중 수익률 | **-1.72%** |
| 분포 | **-5~-2% 에 68건(42%) 집중**, +5% 초과 9건(5.6%) |

→ **작은 손절 반복 + 큰 수익 부재.** 처방은 승률 제고가 아니라 **평균익 확대**,
즉 **트레일링으로 수익을 끌고 가는 것**이다.

사용자 목표("손절선만 깨지 않으면 추적 수익화")와 진단이 정확히 일치한다.

### 1-3. 왜 신규 전략인가

legacy 스캘핑 경로는 `exit_signal.py` 가 **14:50 전량청산**이라 다일 보유 스윙이 성립하지 않는다.
swing_38 을 그대로 쓰지 않은 이유는 §4-2·§6.

## 2. 불변 원칙

1. **운영 청산 프로세스를 새로 만들지 않는다.** `STRATEGY_EXIT_PROFILES` 키 1개 추가로
   `resolve_policy()` → `evaluate_holding()` → 기존 데몬 매도 경로를 탄다.
2. **청산 숫자의 공통 원천은 `AiSwingParams` 다.** `build_exit_plan()`은 전략의
   `ExitPlan`·백테스트 경로가 공유하고, 실제 운영 `HoldingEvaluator`는 같은 파라미터로 만든
   프로파일을 별도 알고리즘으로 평가한다. 두 평가기는 동일하지 않으며 차이는 테스트와 §9로 관리한다.
3. **장부 단일 작성자.** `active_positions` 는 심볼 단일 키 + **무락 upsert**라
   동시 기록자가 늘면 lost-update 위험이 있다.
   → ai_swing **진입 실행은 별도 프로세스가 아니라 `intraday_buy_daemon` 내부 훅**이다.
   `ai_swing_daemon` 은 **관측 전용**(주문 경로를 import 조차 하지 않는다).
4. **데이터가 없으면 만들지 않는다.** 산출물 부재·파싱 실패는 `no_data` 또는 `partial`로
   강등하며 완전한 교집합을 날조하지 않는다. 실진입은 당일의 신선한 `status=ok`만 허용하고,
   예외는 전량 흡수해 라이브에 영향을 주지 않는다 (§7).

              │  status: ok | stale | partial | no_data
              ├──────────────────────────────┬──────────────────────────────┐
              ▼                              ▼                              │
  scripts/ai_swing_daemon.py         scripts/intraday_buy_daemon.py         │
  (관측 전용 · 주문 미배선)            _scan_and_buy 내부 훅                  │

### 3-1. 유니버스 판정 규칙

| 조건 | status | items | 진입 |
|---|---|---|---|
| `BARRO_AI_TRADE_DIR` 미설정/부재 | `no_data` | `[]` | 금지 |
| 두 파일 모두 부재 | `no_data` | `[]` | 금지 |
| 당일 watchlist + 당일 predictions 부재(과거 predictions만 있는 경우 포함) | `partial` | 기본 `[]`; `FALLBACK=scan_only`이면 스캔 단독 | 스캔 단독은 shadow만, 실진입 금지 |
| 둘 다 `date == today(KST)` | `ok` | 교집합 | 공통 신선도 검증 통과 시만 허용 |
| 위 partial 조건 외에 선택된 두 원본의 `date` 중 하나라도 과거 | `stale` | 교집합 | shadow에서 `ALLOW_STALE=1` 시만, 실진입 금지 |
| 교집합 0종목 | 기존 `ok`/`stale` 유지 | `[]`, `reason="intersection_empty"` | 로그 1줄 후 종료 |
| 파싱 실패 | `no_data` | `[]`, `reason="parse_error:<타입>"` | 금지 |

- 교집합 = `set(scan.code) ∩ set(pred.code)`
- 정렬: `pred_score` DESC → `scan_score` DESC → `symbol` ASC
- 코드 정규화는 `kiwoom_native_rank._normalize_symbol` 재사용 (`_AL`/`_NX` 접미사 제거)
- **파서는 lenient** — 미지 필드는 무시한다(strict 검증 금지). ai-trade 스키마가 늘어도 안 깨진다.
- 완전 교집합은 watchlist·predictions 모두, `scan_only` shadow는 watchlist의
  `date == today(KST)`와 `mtime <= MAX_AGE_H`를 같은 검증기로 확인한다.
  `ALLOW_STALE=1`로 허용한 완전 교집합 메시지는 `stale 허용`으로 표시한다. scan-only의
  stale 사유와 history JSON에는 원본 날짜가 명시된다. 어느 stale도 실진입에는 쓰지 않으며,
  `status=ok`만으로 주문 가능하다는 뜻도 아니다.

## 4. 진입 명세

### 4-1. 부모(`Swing38Strategy`)에서 그대로 계승하는 것

`AiSwingStrategy(Swing38Strategy)` — 진입 판정 로직은 **한 줄도 새로 쓰지 않았다.**

```
① 임펄스   최근 30봉 중 양봉 AND gain ≥ 5% AND 거래량 ≥ 전체평균 × 2.0 인 첫 봉
② Fib      retrace = (임펄스high − 현재close) / (임펄스high − 임펄스low)
           |retrace − 0.382| ≤ 0.075 여야 통과 (벗어나면 즉시 거부)
③ 반등     최근봉이 양봉이어야 하고, body = (close−open)/open 을 0.02 기준 정규화

score = (impulse 0.4 + fib 0.4 + bounce 0.2) × 10   →  score < min_score 면 거부
```

선행 가드도 계승: `min_candles=60` · **`require_daily_candles=True`**(캔들 간격 12h 미만이면
거부 — 일봉 전용 스윙) · `min_atr_pct=0.03`.

### 4-2. 바꾼 것

| 항목 | swing_38 | ai_swing | 왜 |
|---|---|---|---|
| **종목 원천** | 당일 주도주 랭킹 | **단테 스캔∩예측 교집합** | 이 전략의 존재 이유 |
| `min_score` | 5.0 (시뮬 진입점) | **3.0** | 이중 게이트(교집합 ∩ swing_38 8단 AND)로 **발화 0 위험**. 완화 스타트 후 shadow 실측으로 조인다. 실측상 점수를 올릴수록 수익이 나빠졌다(§6-3) |
| `signal_type` | `"swing_38"` 리터럴 | `"ai_swing"` | 부모 구현의 하드코딩 때문에 `_analyze_v2`·`add_on_signal` override 필요 |
| 청산 파라미터 | §6 | §6 | 전면 재측정 |

`STRATEGY_ID = "ai_swing_v1"` — `self.STRATEGY_ID` 참조 방식이라 나머지는 자동 전파된다.

### 4-3. 후보 주입 (진입 훅)

**다른 zone 전략과 결정적으로 다른 지점이다.** f_zone/gold_zone 등은 후보를
`KiwoomNativeLeaderPicker`(당일 급등 상위 N)에서 받지만, ai_swing 은 단테 교집합에서 받는다.
두 집합은 성격상 거의 겹치지 않는다(랭킹 = 당일 급등 / 교집합 = 되돌림 대기).

→ `_scan_and_buy` 안에서 교집합 종목을 **`LeaderCandidate` 로 합성해 주입**한다.
합성하지 않으면 ai_swing 은 **영구히 진입 0** 이다.

- 시세는 **읽기전용 일봉 TR(`fetch_daily`)만** 쓴다 — 신규 TR 없음.
  `cur_price` = 마지막 봉 종가, `flu_rate` = 마지막 2봉 종가 변화율.
- 주입된 후보도 기존 유니버스 필터(급등 상한 29.5% · 최소가 5,000원)를 **동일하게** 통과한다.
  레버리지·인버스와 ETF·ETN 제외는 각각 `SUPERTREND_AUTO_EXCLUDE_LEVERAGE`,
  `SUPERTREND_AUTO_EXCLUDE_ETF`가 truthy일 때만 적용된다.
- **종목 격리**: `ai_swing` 신호는 **교집합 종목에서만** 인정한다. 랭킹 후보가 우연히
  ai_swing 시뮬에서 최고점을 받아도 진입시키지 않는다.
- **현재 신호 권위**: 누적 백테스트 PnL을 진입 신호로 쓰지 않는다. shadow와 동일한
  `AiSwingStrategy.analyze()`가 최신 일봉에서 신호를 반환해야 한다. 실진입은 당일 `status=ok`
  두 원본 파일의 수정시간도 `MAX_AGE_H` 이내여야 한다.

## 5. 청산 명세

### 5-1. 공유 파라미터와 분리된 두 평가기

기존 시뮬레이터 `_exit_plan_for_strategy()` 는 **어떤 전략의 `exit_plan()` 도 호출하지 않고**
고정값(TP +3/+5/+7% · **SL -1.5%** · BE +1%)으로 보내며 `min/max_hold_days` 를 설정하지 않는다.

→ **"swing_38 OOS +2.36%" 는 SL -15% 의 근거가 아니다.** 백테스트가 라이브를 대변하지 못했다.

ai_swing 은 전략의 `ExitPlan`과 백테스트가 같은 빌더를 쓰도록 한다:

```python
def build_exit_plan(entry_price: Decimal, p: AiSwingParams, *, symbol: str = "") -> ExitPlan
```

- 전략/보호 경로: `AiSwingStrategy.exit_plan()` → 이 함수에 위임
- 시뮬: `_exit_plan_for_strategy()` **최상단 분기** → `strategy_obj.params` 로 이 함수 호출
- 실제 운영 매도 경로: `HoldingEvaluator`가 `AiSwingParams`로 만든 프로파일을 자체 순서로 평가

따라서 **숫자는 `AiSwingParams`로 공유하지만 평가기는 둘**이다. `build_exit_plan()` 호출 경로끼리는
동일하고, `HoldingEvaluator`의 파라미터 매핑과 의도한 동작은 회귀 테스트로 확인한다.
첫 3일 hard SL 순서는 현재 다르다(§9).

⚠️ 시뮬 분기는 `_apply_rf_stop` 을 **재적용하지 않는다** — `build_exit_plan` 이 이미
`resolve_sl_pct` 를 거치므로 이중 적용을 피한다.

### 5-2. `ExitPlan` 구성

| 요소 | 값 | 비고 |
|---|---|---|
| TP1 | `entry × (1 + tp1_pct)` · 수량 `tp1_qty` | +20% · 50% |
| TP2 | `entry × (1 + tp2_pct)` · 수량 `tp2_qty` | +50% · 50% |
| SL | `resolve_sl_pct(STRATEGY_ID, entry, sl_base, symbol)` | 라운드피겨 보정 경유 |
| BE | `breakeven_trigger = be_pct` | +10% 도달 시 본전 잠금 |
| **트레일링** | `trail_stages = [(trail_start_pct, −trail_offset_pct)]` | §5-3 |
| 보유기간 | `min_hold_days` / `max_hold_days` | 3 / 20 |
| `time_exit` | **없음** | multi-day 스윙 — 당일 강제청산 폐기 |

`sl_base` 는 `BARRO_AI_SWING_SL_PCT` env 가 있으면 param 을 덮는다 (운영 kill-lever).
`trail_start_pct <= 0` 이면 `trail_stages=None` → 트레일링 비활성(그리드로 끌 수 있게).

### 5-3. 트레일링 — 이 전략의 핵심

`trail_stages` 형식은 `[(high_pnl_pct, trail_pct), ...]` DESC 이고
**`trail_sl = peak × (1 + trail_pct)`** 이므로 offset 은 **음수**로 넣는다.

**★구현 중 발견한 결함**: `backend/core/strategy/` 전체에 `trail_stages` 설정이 **0건**이었다.
`ExitPlan.trail_sl_for_peak()` 는 `trail_stages` 가 없으면 `None` 을 돌려주고
그러면 `ExitEngine` 트레일링이 **통째로 비활성**된다.

→ **swing_38 을 포함한 모든 전략이 ExitEngine 경로에서 트레일링 없이 돌고 있었다.**
(`HoldingEvaluator` 경로에만 `trailing_start_pct` 가 별도 구현돼 있어 **두 청산 경로가 어긋난다**.)

사용자 목표의 핵심인 "추적 수익화"가 코드에 아예 없었다는 뜻이다. ai_swing 에 한해 해소했고,
**나머지 전략은 그대로다**(별도 티켓).

### 5-4. 라이브 ai_swing 청산 경로 — 지원 작성자 1개

라이브 ai_swing의 유일한 지원 매도 작성자는 `intraday_buy_daemon._evaluate_and_sell`이다.
이 경로가 미체결 조회, 중복 매도 차단, durable sell intent, 확정 `FILLED` 백필과 장부 대사를
함께 수행한다. 전략 필터 없이 브로커 보유 전체를 평가하므로 ai_swing 장부도 자동 포함한다.

`evaluate_holdings.py --auto-sell`은 같은 프로파일로 판단하지만 위 주문·체결 수명주기가 없어
라이브 ai_swing 작성자로 승인하지 않는다. 이 스크립트는 기본 DRY_RUN도 포지션 장부를 갱신할
수 있으므로 ai_swing 보유 중에는 운영 장부를 보는 cron 자체를 중지한다. 진단이 필요하면 복사한
장부와 별도 `--pos-log`/`--audit-log`로 격리한다. 운영 모델상 `intraday_buy_daemon`을 계속
가동할 수 없다면 ai_swing 실진입도 활성화하지 않는다.

⚠️ `ai_swing_daemon` 은 **매도하지 않는다**(이중 매도 방지). 관측 전용이다.

라이브 `HoldingEvaluator`는 ai_swing의 -5% hard SL을 `min_hold_days`보다 먼저 평가한다.
TP·트레일링 등 나머지 청산은 최소 3일 이후, max-hold는 20일에 평가한다. 보호 경로인
`ExitEngine`은 아직 min-hold 우선이라 첫 3일 hard SL 동작이 다르며 §9의 알려진 한계다.

## 6. 파라미터와 근거

### 6-1. 확정값

```python
min_score        = 3.0            # 부모 5.0 대비 완화
sl_pct           = -0.05          # env BARRO_AI_SWING_SL_PCT 로 override
tp1_pct / tp1_qty = 0.20 / 0.5
tp2_pct / tp2_qty = 0.50 / 0.5
be_pct           = 0.10
trail_start_pct  = 0.10
trail_offset_pct = 0.03
min_hold_days / max_hold_days = 3 / 20   # Swing38Params 계승
```

### 6-2. ★초기 설계와 정반대 방향이 최적이었다

사용자 승인 초안은 **swing_38 계승값**(SL -15% / trail +20%·5%)이었다.
랜덤 유니버스 120종목 × 3 seed 그리드 실측 결과:

| 조합 | 3-seed 평균 | PASS | 승률 |
|---|---:|:---:|---|
| 초기 계승값 (SL -15% / trail +20% / off 5%) | +0.309% | 1/3 | 38.3~41.6% |
| SL 만 조정 (SL -5% / trail +20% / off 5%) | +1.101% | 3/3 | 26.6~28.1% |
| **전면 조정 (SL -5% / trail +10% / off 3%)** | **+2.172%** | **27/27** | **36.0~39.5%** |

**약 7배.** holdout 도 전 케이스 양수(+2.75~4.17%). 세 파라미터가 독립적으로 기여한다.

### 6-3. 단조 패턴 (근거의 견고성)

- **트레일링 격리**: SL 2수준 × 3 seed = **6/6 개선**, 평균 **+0.96%p**. 사용자 가설의 방향이 옳다.
- **`trail_off` 는 좁을수록 우수** (3% > 5% > 8%) — 9/9 쌍 예외 없음.
- **`trail_start` 는 낮을수록 우수** (10% > 15% > 20%).
- **SL 은 좁을수록 우수**. -10%/-12%/-15% 의 FAIL 사유는 **drop1 부호반전** =
  최대 기여 종목 1개를 빼면 평균 부호가 뒤집힌다 → **아웃라이어 의존**.
  넓은 손절이 "대박 1건으로 다수 손실을 덮는" 구조를 만든다.
- **`min_score` 는 올릴수록 나빠진다** (3.0 → 5.0 → 7.0 순으로 악화). 조이는 튜닝은 근거가 없다.

### 6-4. ★승률↔수익률 트레이드오프가 나타나지 않았다

최적값(+10%/3%)은 **수익률과 승률이 동시에** 개선된다 (승률 26~28% → 36~39.5%).
통상의 역상관이 여기서는 깨진다 — 좁은 손절 + 이른 트레일링이 손익비 축을 직접 개선하기 때문이다.

⚠️ 다만 **승률 80% KPI 와는 방향이 다르다.** 이 전략은 승률이 아니라 손익비로 버는 구조다.
(승률 80% 는 별도 두 리포트가 독립적으로 **달성 불가** 판정 — 기대값>0 하 최대 ≈42%.)

## 7. 안전 설계

### 7-1. 5중 default-OFF — 전부 열려야 주문 시도가 생긴다

| # | 게이트 | 기본 | 열려면 |
|---|---|---|---|
| ① | `zone_strategies` 에 `ai_swing` 포함 | 미포함 | `BARRO_DAEMON_STRATEGIES` 또는 `--strategies` |
| ② | `BARRO_AI_SWING_ENABLED` | `0` | `1` — shadow·진입 공통 마스터 |
| ③ | `BARRO_AI_SWING_ENTRY_ENABLED` | `0` | `1` — 0이면 **로더조차 호출하지 않는다** |
| ④ | `BARRO_AI_SWING_BUDGET_RATIO` | `0.0` | `>0` — 0이면 신호가 나와도 전량 차단 |
| ⑤ | `BARRO_AI_TRADE_DIR` + 당일 완전 산출물 | 미설정 | 절대경로, `status=ok` |

상위에 `LIVE_TRADING_ENABLED`(실주문 마스터)와 데몬 `--no-dry-run` 이 **별도로** 있다.
`DEFAULT_ZONE_STRATEGIES` · 시뮬 `DEFAULT_STRATEGIES` 에 **의도적으로 넣지 않았다.**

### 7-2. fail-closed 캡

슬롯(`MAX_POSITIONS`)·예산(`BUDGET_RATIO × (orderable_cash + total_eval)`) 계산에
실패하면 **통과가 아니라 차단**한다. 다일 보유(min_hold 3 · max_hold 20) 포지션을
"모르는 예산"으로 늘리지 않는다. 후보 단계뿐 아니라 실제 주문 수량도 남은 예산의
`floor(잔여예산 / 현재가)`로 제한한다. ai_swing 캡 실패가 **다른 전략 신호를 삼키지 않음**도 테스트로 고정.

이 캡은 주문 직전 조회한 호가로 수량을 제한한다. 시장가 실제 체결가는 더 높을 수 있어 체결 후
평가액이 비율 상한을 소폭 넘을 수 있으므로, 체결 감사 로그와 브로커 잔고로 사후 대사한다.

### 7-3. 슈퍼트렌드와 4중 격리

1. **종목** — 제외 집합 = `balance.holdings` ∪ `active_positions` ∪ `closing_bet_positions`
2. **자본** — `BUDGET_RATIO` × 기준자산을 ai_swing 평가액 상한으로
3. **슬롯** — `MAX_POSITIONS` (기본 3)
4. **이월** — EOD 트림 면제(다일보유)이므로 `BUDGET_RATIO` 를 0.20 이하로 사전 통제

### 7-4. 2단 플래그 — 2026-05-29 사고 재발 방지

swing_38 비활성 시 장부 동기화 누락 + 보유분 자동 청산 부재로 잔여 4종목을
사용자가 수동 청산해야 했다(평균 -0.985%).

- `ENTRY_ENABLED=0` → **진입만** 중단, **청산 권한 유지**
- `ENABLED=0` → shadow와 신규 진입 마스터 정지. 장부 기반 기존 청산은 계속 평가된다.
  보유 중에는 청산 작성자를 유지하고, 완전 종료가 목적이면 **보유 0 확인 후** 내린다.

플래그 OFF 자체가 청산을 유발하지는 않는다. 실행 중 데몬은 `.env.local` 변경을 자동 재로딩하지
않으므로 ENTRY/ENABLED 변경 후에는 해당 프로세스를 재시작하고 새 PID·유효 설정을 확인한다.

### 7-5. 고아 포지션 (장부 유실)

브로커에 보유는 있는데 `active_positions.json` 에 없으면 `HoldingEvaluator` 가 `ctx=None`
경로로 빠져 전략 프로파일을 무시하고 로드된 `data/policy.json`의 base 값으로 평가한다.
개발 파일은 -2%일 수 있지만 파일 부재·파싱 실패 시 `PolicyConfig` 기본 SL은 -4%다.
→ **전략 SL(-5%)·트레일링·min_hold 3일이 전부 무시되고 base 정책으로 전량 손절될 수 있다.**

`scripts/ai_swing_recover.py` 로 진단·복원한다(주문 없음). **복원 원천(`order_audit.csv`)이
없으면 복원하지 않는다** — 확인된 체결수량·평균체결가 또는 `FILLED`만 인정하며 `DRY_RUN`,
단순 `ORDERED`, 미체결·모호한 상계는 거부한다. `entry_time` 을 "지금"으로 채우면
`min_hold_days=3` 이 리셋된다.

라이브 매수는 주문 전 ai_swing provisional intent를 원자 저장해 접수 후 장부 유실
구간을 막는다. 확정적인 게이트 차단일 때만 intent를 제거하고, 접수 시 실제 주문번호로 연결한다.
주문 결과가 불명확하면 intent를 보존하고 이후 주문을 중지해 운영자가 대사할 근거를 남긴다.
매도는 호출 전 `order_audit.csv`에 intent를 fsync해 접수 후 timeout·audit 누락을
복구한다. 이후 브로커 잔고·미체결 대사가 확정 매수·매도 `FILLED`를 멱등 백필하고,
미체결 매도 또는 최근 intent가 있는 종목의 중복 매도를 5분 대사 유예로 차단한다.
미체결 조회나 매도 audit 읽기·쓰기·fsync가 실패하면 이 대사와 장부 변경은
fail-closed로 보류한다.

`--apply` 복구 전에는 관련 cron을 비활성화하고 `active_positions`를 쓸 수 있는 모든 프로세스를
중지한 뒤 `ps`로 부재를 확인한다. 복구가 끝난 후 의도한 작성자와 매도 작성자 하나만 재기동한다.
운영 런북은 세 스크립트의 원장 경로를 맞추기 위해 `BARRO_DATA_DIR` 미설정과
`intraday_buy_daemon`의 기본 `data/` 원장 인자를 실주문 전제로 강제한다.

### 7-6. §2 준수

## 9. 알려진 한계

1. **예측 저장 훅은 별도 ai-trade 레포에 구현됐지만 아직 운영 배포 전이다.** 배포 전에는
   교집합이 성립하지 않는다. `FALLBACK=scan_only` 관측은 반드시 **"단테 스캔 단독"**으로
   표시하며 실진입에는 사용하지 않는다.
2. **그리드는 단테 교집합이 아닌 대조군 기준이다.** 랜덤 유니버스 120종목이며
   캐시 `as_of 2026-06-18`(약 6주 낙후). **shadow 실측 후 재검토 필요.**
3. **라이브와 백테스트의 첫 3일 hard SL 동작이 다르다.** 라이브 `HoldingEvaluator`는 -5%를
   min-hold 전에 청산하지만, 보호 경로 `ExitEngine`은 min-hold를 먼저 적용한다. 이 차이를
   해소한 재백테스트 전에는 과거 수익률을 라이브 기대수익으로 해석하지 않는다.
4. **hold 일수는 달력일이다** (`(now − entry_time).days`). 금요일 진입 시 min_hold 3일이
   거래일 1일 만에 해제되고, max_hold 20일은 거래일 약 14일이다.
5. **데몬 미기동일엔 청산 평가가 스킵된다** (KRX 휴장일 캘린더가 코드에 없다).
6. watchlist는 시스템 날짜, predictions는 KST 날짜를 쓴다. 운영 머신 시간대를
   `Asia/Seoul`로 맞추지 않으면 서로 다른 날짜 파일이 생길 수 있다.
7. **shadow 실측 미시작** — 교집합 종목수·진입 발화율은 실측 전 단정 불가.
   신호 0건이 나와도 곧바로 "전략 미성립"이 아니라 `skipped` 사유 분포를 먼저 본다
   (일봉 60봉 미만·ATR 3% 미만은 구조적으로 신호 0).
8. 주문 수량 캡은 주문 전 호가 기준이라 시장가 체결 미끄러짐으로 실제 평가액이 예산 비율을
   소폭 넘을 수 있다. 현재는 체결 후 자동 감량 대신 운영 대사·진입 중지로 대응한다.
